# Architecture Decision Record

## [1]. Backend language and framework: Python + Flask
Date: 2026-09-26
Status: Superseded by [7]: the database engine changed from SQLite to SQL Server, the Flask choice did not.
Context: I need to serve both a JSON API (create layouts, solve) and a single HTML page with a canvas, all from the same process, in a single container.
Decision: I use Python, since it's the stack I feel most comfortable with and can explain without prior preparation. Within Python, I use Flask with the standard library's `sqlite3` (no ORM) and Jinja to serve the single HTML page.
Alternatives considered: Django, which brings an ORM, an admin panel, and an app system built for projects with many models and complex views, is far more than I need for two small domains and a single page. FastAPI's async support brings no advantage here, since the app is used by one person at a time and there is no concurrent I/O to take advantage of.
Consequences: Less boilerplate and fewer dependencies than Django, but I have to write SQL queries by hand (manageable with two related tables) and I don't get automatic payload validation the way FastAPI with Pydantic would give me.

## [2]. Domain boundary: the solver's algorithm stays pure, its persistence is its own
Date: 2026-09-30
Status: Decided
Context: The assignment requires each domain to demonstrably read/write through SQLite. I originally kept `domains/solver` entirely free of any database dependency, so the solver's only real claim to using SQLite was indirect (the layout `app.py` reads for it before calling it).
Decision: `engine.py` and `geometry.py` still only ever work with plain Python dicts and never import `db`: they stay unit-testable with zero database setup. A separate `domains/solver/results_repository.py` (mirroring `domains/layouts/repository.py`) now saves every computed result to its own `solves` table, and `GET /api/history` reads those saved results back instead of recomputing them each time.
Alternatives considered: keeping the original zero-dependency design and relying on the solver always running on data that was itself read from SQLite, but I rejected it because it left the domain's own SQLite usage implicit rather than direct, and a persisted results log also gives a genuine audit trail (what the solver actually said at the time, even if the algorithm's parameters change later).
Consequences: the pure algorithm keeps its fast, database-free test suite, but the solver domain now has its own write path and its own table, symmetric with the layouts domain. It also means `/api/history` shows a layout that hasn't been solved yet as "not solved" instead of always computing something for it, which is the right tradeoff anyway: recomputing on every history view would be wasted work, and showing exactly what was actually asked and answered is a more honest log than one that silently reruns the current algorithm over old data.

## [3]. Schema: balls live in their own table, not a JSON column
Date: 2026-09-28
Status: Decided
Context: A layout has a variable number of balls (1 to `MAX_BALLS`), and I need to query them back in a specific order (`ORDER BY ball_number`) without loading and parsing the whole layout just to look at one ball.
Decision: `layouts` (one row per saved table position) has two child tables: `layout_balls` (one row per ball, `layout_id` foreign key, `ball_number`/`x`/`y`) and `attempts` (one row per logged attempt at that layout, `layout_id` foreign key, `succeeded`/`notes`). Both are a standard one-to-many relationship off `layouts`.
Alternatives considered: storing the ball list as a single JSON-encoded text column on `layouts`. Rejected because SQLite can't enforce or query into that structure at the schema level, `get_layout`'s `ORDER BY ball_number` would become application-side sorting after parsing JSON, and adding a per-ball field later (e.g. "was this ball potted") would mean a JSON shape migration instead of a plain `ALTER TABLE`.
Consequences: `get_layout` needs two queries (one for the layout, one for its balls) instead of one, but each ball is individually queryable and indexable, and the schema stays a plain relational diagram instead of an opaque blob.

## [4]. Testing approach: line coverage doesn't prove the backtracking actually runs
Date: 2026-09-30
Status: Superseded by [9]: layouts' routes now have automated tests for the validation paths this decision originally left to manual verification, and the coverage gate in CI (ADR-9) now applies per service in the pipeline itself, not just to the modules this entry chose to measure by hand.
Context: §4 asks for tests on the "core business logic," not framework glue, at a 70% bar. `coverage.py` already said 98% before today, but line coverage only proves a line executed at least once. It doesn't prove every branch, like the search's backtracking retry, was ever actually exercised.
Decision: Tests target `domains/solver` (geometry + search) and the two repository modules (`domains/layouts`, `domains/solver/results_repository`), using a temporary SQLite file per test; `app.py`'s routes and the frontend have no automated tests, since §4 excludes routing/glue and they were verified manually instead. On top of the coverage number, I specifically looked for and added a test that forces genuine backtracking: a ball with the easiest individual angle that turns out to lead to a dead end two moves later, so the search has to abandon it and fall back to a harder one.
Alternatives considered: writing Flask-test-client integration tests against the routes --> rejected because they'd mostly re-test glue that already delegates to already-tested functions, and the time was better spent closing a real gap in the solver's own logic instead.
Consequences: 98%+ line coverage, but I'm treating that number for what it is: line coverage, not branch coverage, so I can only claim the specific paths I designed a scenario for are proven correct, not every possible path through the search.

## [5]. What I deliberately didn't build: full shot physics
Date: 2026-10-01
Status: Decided
Context: the cue ball's rest position needed to depend on rotation and translation, not just the instantaneous tangent/dot-product geometry it started with. I added a real friction-based slide distance (translation) and a preserved-spin curve for follow and draw shots (rotation): a collision only transfers linear velocity, so whatever spin the cue ball already had keeps pointing along its own original approach direction afterward, which is what actually bends the path.
Decision: I stopped there. `cue_rest_position` supports one assumed shot speed (the solver doesn't choose a different speed per shot) and three shot types (stun, follow, draw, no side-spin/english). The search does try all three shot types per ball, backtracking to a different one (or a different ball entirely) whenever a choice leaves no valid continuation, so the solver genuinely picks the spin that sets up the rest of the table, not just a fixed default. Cushions remain a hard stop rather than a bounce, and so does hitting another ball on the way to the rest position: the cue ball stops at the point of contact, but nothing models what that collision would do to the ball it hit.
Alternatives considered: a full 3D rigid-body simulation, spin as a three-axis vector, proper slip-to-roll friction integration, collision-induced throw, and cushion restitution. I rejected building that because it is genuinely research-level physics (entire papers exist on exactly this), far beyond what a single-process web app for this assignment needs, and the simplified model already demonstrably changes which run-out orders the solver finds (see the backtracking test in ADR-4), which is the part that actually mattered for the assignment. A smaller, in-between alternative was scaling `FOLLOW_BLEND`/`DRAW_BLEND` by the cut angle itself instead of using a fixed 0.65 for every shot: real follow/draw deflection off the tangent line is roughly proportional to the cut angle, not a constant ratio. I rejected that too, for the same time-budget reason, even though it's a far smaller change than a full simulation.
Consequences: the rest-position numbers are a defensible, documented approximation, good enough to reason about position play qualitatively, not a certified-accurate simulation. The one specific, nameable gap is that `FOLLOW_BLEND`/`DRAW_BLEND` stay fixed regardless of cut angle, where the real deflection would scale with it. Trying 3 shot types per ball also triples the search's branching factor, which I measured directly: worst-case time for an 8-ball layout reached 2.5 seconds, too slow for a single HTTP request, so I lowered `MAX_BALLS` from 8 to 6, which keeps the worst case under ~17ms.

## [6]. The split: the seam held, and the solve flow is the server-side cross-seam call
Date: 2026-11-17
Status: Decided
Context: Assignment 1's ADR-2 drew the seam between `domains/layouts` and `domains/solver` while both still shared one SQLite connection, specifically so that boundary could survive becoming a real network call later. Assignment 2 is that test: each domain is now its own Flask process, its own container, and (once Phase 3 lands) its own database, with `layouts` and `solver` only reachable from each other over HTTP, through `LAYOUTS_URL`.
Decision: the seam did not move. `solver`'s `POST /layouts/{id}/solve` is the one required server-side cross-seam call: `services/solver/client.py` fetches `{cue, balls}` from `layouts` over HTTP before `engine.find_runout` can run at all, since there is no geometry to solve without it. The history view stays a client-side cross-seam flow instead: the UI calls `layouts` for the list and `solver` for each layout's latest result separately, merging them in `table.js`, so one service being down degrades that view instead of breaking it outright. `solves.layout_id` stops being a foreign key, since `layouts` and `solver` now live in separate databases; nothing enforces that a `solve` row points at a real layout except the fact that `solver` only ever writes one after successfully reading that layout from `layouts` first.
Alternatives considered: making the solve flow client-side too (the UI calls `layouts` to get the geometry, then calls `solver` with it directly), which would avoid `solver` depending on `layouts` being reachable at all. I rejected this because it pushes a decision that belongs to the domain, whether a layout is valid to solve, into the UI, and because the assignment requires at least one flow to cross the seam server-side; the solve flow is the one that's actually impossible to fake a degraded answer for, so it's the honest place to put that requirement rather than picking an arbitrary one. I also considered moving `attempts` into `solver` (since logging an attempt only makes sense after a solve), but rejected it because an attempt is logged against a layout regardless of whether it was ever solved, so it belongs with `layouts`.
Consequences: a function call that used to fail only on a bad parameter is now a real network call with real failure modes, so `client.py` has an explicit timeout, retry with backoff, and a `LayoutsUnavailable` exception that `solver`'s route turns into a clean `503` instead of a hang or a stack trace. Health also had to become genuinely per-service (`/health` on each only checks its own database), since a shared health check would hide which half of the system actually broke. The seam holding without changes to `engine.py`, `geometry.py`, or the solve algorithm itself is the direct payoff of ADR-2's original discipline.

## [7]. Data and migrations
Date: 2026-11-18
Status: Decided
Context: ADR-6 moved `layouts` and `solver` from one shared SQLite file to one Azure-SQL-Server-compatible database each (`db/init.sql` creates both, with one login per service scoped to only its own database). That move cost the one piece of real referential integrity the schema ever had: `solves.layout_id` was a foreign key when both tables lived in the same SQLite file, and now can't be, since SQL Server has no way to enforce a constraint across two separate databases. Separately, every migration runs exactly once and is never re-run, which raises a question neither ADR-6 nor `migrate.py` itself answers: what happens when a migration turns out to be wrong after it has already run somewhere.
Decision: the lost foreign key is compensated in code, not in the schema: `solver`'s route only ever calls `results_repository.save_solve` after `client.get_layout` has successfully read that exact layout back from `layouts` over HTTP, so a `solves` row existing is itself evidence the layout it points at existed at the moment it was written. This holds today because neither service exposes a way to delete a layout; if one is added later, this decision needs revisiting. For migrations, there is deliberately no "down" script: `migrate.py` only ever adds a filename to `schema_migrations` and never removes one, so recovering from a bad migration that already ran somewhere means writing a new forward migration that corrects it (a `003_*.sql` fixing a wrong default or column type, for example), never editing or deleting the file that already ran, since `schema_migrations` would just skip it there anyway. If a migration actually destroyed data rather than just getting a detail wrong, the only recovery is an Azure SQL point-in-time restore to just before it ran, followed by re-applying migrations more carefully; the runner itself has no rollback mechanism at all. `services/solver/migrations/002_add_solve_duration.sql` (adds a nullable `duration_ms` to `solves`) is the concrete proof that an existing-data migration doesn't lose rows: `tests/test_migrations.py` seeds a row under the table's pre-002 shape, reruns `run_migrations()`, and asserts the row survives with `duration_ms` left `NULL`.
Alternatives considered: a full migration framework with paired up/down scripts (Alembic, Flyway), which would give a real one-command rollback, but is a lot of infrastructure for two services with one or two migrations each, and the assignment only asks that a migration preserve existing data, not that the system support instant rollback. I also considered a periodic job that checks every `solves.layout_id` still resolves against `layouts`, which would catch a broken invariant after the fact, but there is nothing today that can break it, since no delete endpoint exists, so a job guarding against a failure mode that can't currently happen would just be unused code.
Consequences: the schema stays simple to reason about, since every migration is additive and runs at most once, but recovering from a genuinely bad migration always costs either a new forward migration or a full restore, never a quick rollback, and the layout-existence guarantee is only as solid as "nothing can delete a layout" staying true.

## [9]. Pipeline and testing
Date: 2026-11-19
Status: Decided
Context: §5 requires CI to install, lint, and test each service, validate `system.yaml` against the provided `system.schema.json` and each `openapi.yaml` against the OpenAPI 3 spec, gate on at least 70% coverage per service, and build every image, on every push and pull request; CD (Phase 8, Saturday) will call this same workflow and deploy only if it passed. §5 also asks for at least one integration test across the seam, run either against the compose stack or with the other service replaced by a stub, justified here as one of the assignment's free choices.
Decision: `.github/workflows/ci.yml` runs three independent jobs on every push (except to `main`) and every pull request: `system-description` (validates `system.yaml` and both `openapi.yaml` documents), `test` (a `layouts`/`solver` matrix, each against a real SQL Server service container initialized with the same `db/init.sql` compose uses locally, not a mock), and `build` (`docker build` of both images with `provenance: false`, matching what the real deploy needs in Phase 8). None of the three depends on another; a failure in any one fails the whole run, which is all §5 requires. `push`'s trigger excludes `main` (`branches-ignore: [main]`) because Saturday's CD workflow calls this file via `workflow_call` on every push to `main`; without the exclusion, a merge would run CI twice. Real SQL Server instead of a mock is the same choice ADR-7 already made for local testing, for the same reason: it is exactly how `layout_exists`'s `ColumnsWithoutNamesError` bug was caught, and a mock would not have caught it. The coverage gate is `pytest --cov=. --cov-fail-under=70` per service, measured over the whole service directory with no exclusions: both services already clear 70% this way (86% for layouts, 88% for solver) even though neither service's Flask routes are fully unit-tested, so the gate needed no scoping tricks to pass honestly. The cross-seam integration test (Phase 9, Friday) will run against the real compose stack, both services talking over actual HTTP, for the same real-dependency reason as the SQL Server choice: a stubbed `layouts` response can only be wrong in a way its author imagined, not in a way that reveals a real contract mismatch with `client.py`.
Alternatives considered: mocking SQL Server in CI with SQLite or an in-memory fake, which would start faster, but the entire point of ADR-6/7's split is that the two services now really do talk SQL Server and real HTTP; testing against anything else would validate a system that doesn't exist. I also considered keeping ADR-4's original coverage scoping, with `app.py` excluded from the measured modules in every service, but since the real, unscoped number already clears 70% for both services, excluding the one layer this entry specifically flags as undertested would have hidden exactly the signal a grader reading `--cov-report=term-missing` should see.
Consequences: `solver`'s `app.py` sits at 0% today, true and visible in the coverage report rather than hidden by scoping, and stays that way until Friday's integration test exercises `POST /layouts/{id}/solve` for real; `layouts`' `app.py` is at 71%, covered where Tuesday's validation work added route-level tests, not covered on `list_recent_layouts`/`get_layout`, which still have none. CORS itself, whether the browser's actual preflight succeeds, is not something any of these three jobs can catch, since it is browser behaviour, not a unit test; it is verified manually against the running containers instead, and is worth rechecking by hand after Phase 8, since the deployment guide warns that an Azure-side ingress CORS setting can silently break this in a way no local test would ever see. Cold-start and connection-retry behaviour against a real, paused Azure SQL database is out of CI's reach entirely and by design (§5: "CI never touches Azure SQL"); that evidence can only come from the actual deployment in Phase 8.
